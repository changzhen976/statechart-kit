# 0.13.0 — 事件可见性与 internal-only 保护

> 历史记录：0.15 已用 `internalOnlyEvents` 重新设计并删除 external-only；本文中的 `eventVisibility` / external 不再代表当前实现。

> 状态：已实现（0.13.0）
>
> 分支：`feat/0.13-event-visibility`
>
> 目标版本：`0.13.0`；0.12.0 保持现状，不混入本变更。

## 1. 问题

全页编辑器的事件面板把接收事件统一显示为「转移监听」，没有区分：

- 真正的 SCXML 内部事件（`<raise>`、`<send target="#_internal">`）；
- kit 自动生成的内部延时事件；
- 外部注入事件；
- 同时存在内部/外部来源的事件。

同时，SCXML 没有“该事件只允许内部触发”的声明。并行区域通过内部事件同步时，
宿主外部注入同名事件可能改变时序。

## 2. 目标

1. 事件面板能显示事件来源通道：内部 raise、内部 send、自动延时、外部来源、转移监听；
2. 作者可以把事件标记为「仅内部」；
3. 标记后，外部同名事件不能触发该事件的转移；
4. 保持标准 SCXML，不引入私有命名空间或自定义解释器语义；
5. 现有文档默认行为不变。

## 3. 非目标

- 不实现 external-only 事件（首版只做 `internal` / `both`）；
- 不实现跨会话路由、MQTT 过滤或 invoke 通道；
- 不改变自动延时的 `after` 语义；
- 不做事件总线/ACL；
- 不做画布级事件分组重构。

## 4. 设计决策

### 4.1 数据模型

```ts
export type EventVisibility = 'both' | 'internal'

export interface ProjectDoc {
  // ...existing fields
  eventVisibility?: Record<string, EventVisibility>
}
```

- 缺省 = `both`；
- 保持 `formatVersion: 1`，字段可选；
- `normalizeDoc` 清理空键、非法值回退 `both`；
- 这是 kit 语义，不放进宿主自由使用的 `eventAttrs`。

### 4.2 内部事件动作

新增 DSL：

```text
raise <event>
```

- 解析为 `{ type: 'raise', event }`；
- 序列化为 `<raise event="..."/>`；
- 导入 `<raise>` 时保留为 `raise`，不再降级为普通 `<send>`；
- 首版不支持带 data 的 `<raise>`（SCXML raise 本身没有 data）。

`<send target="#_internal">` 首版仍按外部 send 处理并保留现有 warning；
后续再扩展 `send ... target`。

### 4.3 标准守卫

对标记为 `internal` 的事件，序列化器给监听转移加标准条件：

```xml
<transition
  event="parallel.go"
  cond="(_event.type === 'internal') &amp;&amp; (原有条件)"
  data-kit-visibility="internal"
  target="next"
/>
```

- `_event.type` 是 SCXML 标准系统变量字段；
- 同时写 `data-kit-visibility="internal"`，供导入器识别/剥离守卫；
- 用户原有 `cond` 用括号保护；
- 条件为空时只写守卫。

### 4.4 多事件转移

`event="a b"` 的可见性处理：

- 只有所有事件都是 `internal` 时才加守卫；
- 混合 `internal` / `both` 时**不加守卫**，并产生结构 warning：
  `structure.transition.mixed-event-visibility`；
- 建议作者拆成多条转移；不做自动拆分。

### 4.5 自动延时例外

kit 自动延时由 `<send delay>` 产生，引擎中的 `_event.type` 是 **external**。

因此：

- 自动延时事件不参与 internal-only 守卫；
- 自动延时事件不出现在可见性编辑列表；
- 如有人把同名事件标记为 internal，校验给出 warning；
- 保留现有唯一事件名与 sendid 机制。

### 4.6 导入/导出 round-trip

序列化器写：

- 转移 `data-kit-visibility="internal"`；
- 生成的 `_event.type` 条件。

导入器：

- 若存在 `data-kit-visibility="internal"`：
  - 从 `cond` 剥离 kit 生成的守卫；
  - 把该转移的所有事件写入 `doc.eventVisibility[event] = 'internal'`；
- 若没有元数据，则把条件当作用户条件原样保留；
- 自产 SCXML 的 `serialize → import → serialize` 必须逐字节相等。

### 4.7 UI

事件面板「接收事件」增加：

| 列 | 内容 |
| --- | --- |
| 事件 | 名称 |
| 来源 | `内部 raise` / `内部 send` / `自动延时` / `外部来源` / `转移监听` |
| 可见性 | `双向` / `仅内部` 下拉 |

- 来源由 `DocEventFacts` 的 origin channel 推导；
- 可见性写 `ProjectDoc.eventVisibility`；
- 自动延时行只读，不显示可见性下拉；
- 英文 labels 同步。

### 4.8 宿主过滤（辅助）

编辑器 `sendEvent` 对 `internal` 事件提前拒绝并写日志：

```text
事件 X 仅允许内部触发，已忽略外部注入
```

不把过滤逻辑放进 `SessionRunner.send` 的核心路径，避免改变底层布尔语义；
宿主直接使用 `SessionRunner` 时可用导出的 `isInternalOnlyEvent(doc, name)` 自行判断。


## 4.9 事件术语与 UI 文案

事件需要拆成两个**独立维度**，不能用一个词同时表示“谁发出”和“谁可以触发”。

### 发起方式（来源）

| 取值 | 中文 | 含义 |
| --- | --- | --- |
| `raise` | 发起内部事件 | 进入当前会话内部队列 |
| `send` | 发送事件 | 走 SCXML Event I/O；默认是外部队列 |
| 两者都有 | 双来源 | 同名事件既可 raise，也可 send/外部注入 |

对应 UI 来源标签：

- `内部 raise`
- `本机 send`
- `外部来源`
- `自动延时`
- `仅监听`

### 接受范围（可见性）

| 取值 | 中文 | 行为 |
| --- | --- | --- |
| `internal` | 仅内部 | 只允许 `_event.type === 'internal'` |
| `external` | 仅外部 | 只允许 `_event.type === 'external'`（0.13 不做） |
| `both` | 双向 | 内部、外部都允许（默认） |

完整对照：

```text
内部事件  ↔  外部事件  ↔  双向事件
仅内部    ↔  仅外部    ↔  双向接受
内部发起  ↔  外部发送  ↔  双来源
```

### 文案规范

| 场景 | 推荐 |
| --- | --- |
| 动作 | 发起内部事件（raise） |
| 外部动作 | 发送事件（send） |
| 来源 | 内部 raise / 本机 send / 外部来源 / 自动延时 |
| 可见性 | 双向 / 仅内部 /（后续）仅外部 |

不使用：

- 「抛出事件」：容易被理解成异常；
- 「触发事件」：容易和触发转移混淆；
- 「内部发送」：容易和 `<send target="#_internal">` 混淆；
- 「广播」：`raise` 不是广播。

### 语义注意

- `<send event="x" target="external">` 是出站事件，不等于当前会话的接收事件；
- 普通 `<send event="x">` 默认进入外部事件队列，仍是 external 类型；
- 自动延时是 external 类型，不能套 internal-only 守卫；
- `external-only` 若后续实现，守卫为 `_event.type === 'external'`，但会同时允许
  本机 send 和自动延时；若要严格区分“宿主外部”和“本机 send”，需要额外来源元数据；
- 0.13 只实现 `internal` / `both`，`external` 保持后续需求。

## 6. 验收

- `raise` 生成的 SCXML 与导入 round-trip 稳定；
- internal-only 事件：`_event.type=internal` 触发，外部同名事件不触发；
- 自动延时转移在加入可见性后仍正常触发；
- `done.state.*` / `error.*` platform 事件不受影响；
- 混合事件转移产生 warning，不静默加错误守卫；
- 事件面板能显示来源和可见性；
- 编辑器外部注入 internal-only 事件被拒绝；
- `npm run verify:all` 全绿；
- 真实浏览器验证事件面板与仿真。

## 7. 风险

| 风险 | 影响 | 缓解 |
| --- | --- | --- |
| 其他解释器不实现 `_event.type` | 守卫失效 | 这是 SCXML 标准字段；文档注明运行时要求 |
| 自动延时是 external | 守卫误杀延时转移 | 自动延时例外 + 回归测试 |
| `raise` 导入仍丢失 | 内部事件无法表达 | 阶段 1 先修导入/导出 |
| 守卫写入 `cond` 后重复叠加 | round-trip 条件膨胀 | `data-kit-visibility` + 导入剥离 + 逐字节测试 |
| 混合事件名 | 守卫语义不明确 | 只对全 internal 加守卫，混合 warning |
| 用户条件含 `_event` | 条件组合错误 | 括号包裹 + 组合测试 |
| 图表内部普通 `<send>` 同名事件 | 仍可触发 | 明确文档：internal-only 只拦截“外部类型”事件 |
| 宿主未标记事件 | 无保护效果 | UI 明示默认 both；文档示例 |
| `ProjectDoc` 字段变更 | 老存档兼容 | 可选字段，normalize 默认 both |
| 新诊断 code | 文档/目录漂移 | 更新 `docs/messages.md` 与 code 目录测试 |
